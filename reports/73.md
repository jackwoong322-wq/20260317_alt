## API Shape Check

Local backend checks confirmed:

- `GET /api/dashboard-data`
  - Keeps legacy top-level coin-keyed object.
  - Does not add top-level `data_version`.
  - `?force_refresh=true` does not bypass cache behavior.
- `GET /api/dashboard-manifest`
  - Returns wrapper fields: `data_version`, `generated_at`, `cache_status`, `default_coin_id`, `default_cycle_number`, `coins`.
- `GET /api/dashboard-initial-data`
  - Returns wrapper fields and `data`.
- `GET /api/dashboard-cycle-data`
  - Returns wrapper fields and one `cycle` payload.

Warm local response samples:

- `/api/dashboard-manifest`: about `63ms`, `6.7KB`
- `/api/dashboard-initial-data`: about `40ms`, `46.9KB`
- `/api/dashboard-cycle-data?coin_id=ethereum&cycle_number=5`: about `595ms`, `45.7KB`
- `/api/dashboard-data?force_refresh=true`: about `1862ms`, `2766.2KB`

First local legacy `/api/dashboard-data` call was still slow, about `7.9s`.

## Matches The Spec

- Legacy `/api/dashboard-data` response shape is maintained.
- New manifest, initial, and cycle APIs use wrapper metadata.
- `data_version` is backend snapshot-style metadata, not a DB run id.
- React initial loading uses manifest and initial APIs instead of `/api/dashboard-data`.
- `ALL_DATA` receives `initialResponse.data`, while meta and manifest stay in separate `window` objects.
- Lazy loading uses `ensureCycleLoaded()` and `getCycleStatus()`.
- `loadingCycles` is implemented as `Map<string, Promise<void>>`.
- Direct shell fallback is limited to development-style direct usage, while deployed React flow uses `VITE_API_URL` injection.

## Spec/Implementation Gaps

### High: 032 internal refresh hook is missing

The spec says `032_train_and_predict_box.py` should call `POST /api/internal/dashboard-cache/refresh` after successful Supabase delete/insert.

Current code has the backend internal refresh endpoint, but `032_train_and_predict_box.py` does not read:

- `DASHBOARD_CACHE_REFRESH_URL`
- `DASHBOARD_CACHE_REFRESH_SECRET`

and does not call the internal refresh endpoint after prediction save completion.

### High: cycle API is not a pure single-snapshot projection

The spec says the new APIs should project from one dashboard snapshot cache.

Current implementation uses the snapshot manifest for metadata, but `/api/dashboard-cycle-data` builds the requested cycle payload with targeted Supabase reads. This is faster and more realistic than loading the full dashboard snapshot, but the document still describes a stricter single-snapshot projection contract.

Decision needed:

- Update the spec to describe the current targeted cycle-read design, or
- Change implementation back to full snapshot projection.

Given the original performance issue, the targeted cycle-read design is likely the better MVP direction.

### Medium: legacy stale-cache fallback is incomplete

The spec says that if a cache rebuild fails and a previous cache exists, the backend should keep and return the stale cache.

The new snapshot path has stale fallback behavior, but the legacy `/api/dashboard-data` cache path does not clearly wrap rebuild failure and return stale data.

### Medium: current cycle selection priority differs

The spec says current cycle selection should prefer explicit `is_current`, then fallback to max cycle number, then label parsing.

Current implementation still uses `cycle_name` containing `current` before max cycle fallback.
